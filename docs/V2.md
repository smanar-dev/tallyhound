# Tallyhound v2: email-first on a white-labelled mail layer (November 24, 2026)

Source: `Tallyhound_v2_Email-first_on_a_white-label_Neeter_layer_Tech_Spec.pdf`. This file says what was built, where it lives, what the spec's decisions came to, and where the build differs. Tickets T-171 to T-181.

**One paragraph.** Every request and follow-up is now one letter by email listing everything the client still owes, with their private upload link. Every document comes in through that link (or as an attachment to a reply). Texting is switched off for every firm made from now on. A mail layer (Neeter, named only here, in the adapter and in the subprocessor list) sends the letters from each preparer's own mailbox, reads the replies and keeps a copy of who owes what. Tallyhound keeps the checklist, the pace, the upload page, the sniff test, the review queue and filing, and is the record: the layer's list is a copy that is repaired from ours.

## What is not real yet

Read this first.

- **The adapter is written to a contract Neeter has not confirmed.** Neeter has not published the operations of its interface. `apps/server/src/integrations/neeter/index.ts` uses the addresses and field names in "What Tallyhound needs from the layer" below. Nothing has been run against Neeter. Four of those operations need Neeter to build something it does not have today (spec section 4): making an assistant with no Neeter sign-in, sending a letter on demand in Tallyhound's words, sending with no click, and delivering replies to us. **Get those four confirmed in writing before relying on any of this.**
- **Everything is tested against a stand-in** (`integrations/neeter/fake.ts`): the mirror, retries, the outage, drift repair, the webhook, mailbox connection. Google's and Microsoft's sign-in is tested against stand-ins too.
- **The product runs today without the layer.** With `TH_MAIL_LAYER` unset, an email-first firm's letters go from its Tallyhound address through Tallyhound's own mail service (Postmark), and replies come back there. This is the spec's "fallback sender", and it is the default. It loses only the "from the preparer's own mailbox" benefit.

## What Tallyhound needs from the layer

This is the contract the adapter is written to. Change the adapter, not the interface, when Neeter answers. The full version is `docs/neeter/contract.json` (OpenAPI 3.1), and a test fails if it and the adapter disagree. `docs/neeter/BRIEF.md` is the same thing written to send Neeter; `docs/neeter/RUNBOOK.md` is go-live, step by step; `docs/neeter/AGREEMENT.md` is what the contract with Neeter must cover.

| Operation | Request | Needs building at Neeter? |
|---|---|---|
| Make a firm's key | `POST /v1/keys` with the partner key | Confirm |
| `provision` | `POST /v1/assistants` `{external_id, provider, address, refresh_token, scopes, white_label, signature: false, auto_send: true}` | Yes |
| `upsertProject` | `POST` / `PUT /v1/assistants/{a}/projects` `{external_id, name, contact_email, closed, due_date}` | Supported on its board; confirm through the interface |
| `upsertTask` | `POST` / `PUT .../projects/{p}/tasks` `{external_id, title, owed_by: "client", status, note}` | Same |
| `sendLetter` | `POST .../projects/{p}/letters` `{to, subject, body, thread_id, list_unsubscribe, send_now, add_signature: false}` | Yes (wording, on demand, no click) |
| `getProject` | `GET .../projects/{p}?include=tasks,history` | Confirm |
| `remove`, `forgetProject` | `DELETE` | Confirm the time limit |
| Replies and bounces | Neeter calls `POST /hooks/neeter` `{id, type: "reply" or "bounce", assistant_id, from, to, text, proposed_status, attachment_count, attachments: [{name, content_type, content_base64}]}` with header `x-layer-signature: t=<unix>,v1=<hmac-sha256 of "t." + body>` | Yes |

Every write sends an `Idempotency-Key`. Statuses are Open, Completed, Done, On hold, Canceled.

## Decisions

| | Decision in the spec | What was built |
|---|---|---|
| 1 | Email-first, no texting at launch | Yes. Every firm the service makes is email-first (`firm.letters`). The texting code is still in the repository, switched off, for the later link-only nudge |
| 2 | $5 a client a season | **Not built: "hold off on pricing for now".** Plans and billing are unchanged. For the pilot, leave card billing off and set each pilot firm's plan with the admin command, so nothing is charged (TH-BIL-23) |
| 3 | Approve-each as the pilot default | Yes. A new firm approves each letter; an owner can switch the firm or one client to send on its own |
| 4 | A person confirms every sniff result | Yes, on for every new firm (`confirmAll`) |
| 5 | Tallyhound owns the sign-in app | Yes. The Google and Microsoft app keys are Tallyhound's (`GOOGLE_CLIENT_ID`, `MICROSOFT_CLIENT_ID`); the token is handed to the layer and a sealed copy is kept only so the permission can be withdrawn |
| 6 | Spanish after the pilot | Yes. The letters have Spanish wording that nobody fluent has reviewed; it stays off (T-31) |
| 7 | Kill criteria | Not code. Agree them before January 15 |

Earlier decisions this reverses:

- **"Tallyhound never connects to a firm's mailbox"** (`docs/INTEGRATIONS.md`, November 2026). With the layer on, a preparer's mailbox is connected, by that preparer, with their own consent, and they can disconnect it in one click. Without the layer nothing is connected.
- **"Who writes each message is the owner's choice"** (`docs/REBRAND.md`, decision 1). In an email-first firm no model-written text reaches a client: letters and replies use the fixed wording of the firm's voice.
- **"One document per message"** (the delta spec's C1). A letter lists everything.
- **"A claimed message is never sent again automatically."** Still true for texts, calls and Tallyhound's own mail service. A letter that could not reach the mail layer is tried again for a day with the same key, which the layer must honour (TH-NTR-3). If Neeter cannot promise that, turn the retry off in `pipeline.js` (search `letter_waiting`).

## Where the build differs from the spec

- **No `neeter_link`, `neeter_outbox` or `upload_link` tables.** The mirror's state and the season link live on the engagement inside the firm's sealed record, so they are saved in the same write as the change that caused them and never sit in the database in the clear. The outbox is the difference between what Tallyhound holds and what it last wrote to the layer, worked out on every save and by the timer. Only `mailbox_connection` and `mail_layer_key` are tables (`db/migrations/017_email_first.sql`).
- **The link's token is kept, sealed, not only its hash.** Every follow-up letter must carry the same link, so the token has to be recoverable. It is inside the sealed firm record and never reaches a browser or a log.
- **Paths.** The spec's `/v1/...` paths are the existing `/api/act` actions (`start`, `approveMsg`, `stopAll`, `rotateLink`, ...), `/api/mailbox*`, `/u/{link}` and `/hooks/neeter`.
- **Sign-in is unchanged.** Staff still sign in with an emailed link and two-step sign-in. "Sign in with Google" was not added; connecting the mailbox is its own step under Settings, Mailbox. Say if the pilot needs one-button sign-up.
- **Microsoft cannot be told to withdraw one app's permission** by that app. On disconnect the token is forgotten here and at the layer, and the page tells the preparer where to remove Tallyhound in their Microsoft account. Google's permission is withdrawn at Google.
- **The fix after a bad upload is on the page, not in a second email.** The next letter says what was wrong with the copy ("the copy you sent was for 2025"). A bad attachment sent by email is answered by email.
- **Replies that arrive with a document** are answered once, with the document. Only words on their own go through the reply table.
- **The reminders start over when the client does something** (uploads, replies). The spec's table gives the days for a client who never answers; that case follows it exactly.
- **The delta spec's plan view, call card and activity log** were already built and are still there. The Plan tab is hidden for email-first firms until it is redrawn for letters.
- **Letter wording can be read but not yet edited** under Settings, Message wording: the editor was built for one-line messages. An owner can still edit any single letter before approving it; the client's link is put back by the server, and a letter with its link cut out is refused.
- **Staff screens.** For an email-first firm nothing on any screen mentions texting; a browser test visits every screen to check. Settings has a Mailbox tab (connect and disconnect, the daily limit, the human check and its agreement by form) and Working days in place of sending hours.
- **Sending limits.** `MAIL_CAP` is 1,000 a day for Google and 5,000 for Microsoft: half of the business-account limits as commonly published. Confirm them, and set a lower number under Settings for a firm on a personal mailbox.

## Running without the layer, and switching it on

`TH_MAIL_LAYER` unset: letters from each firm's Tallyhound address, replies to it. Nothing to connect.

`TH_MAIL_LAYER=neeter`: needs `NEETER_BASE_URL`, `NEETER_PARTNER_KEY`, `NEETER_WEBHOOK_SECRET`, and a Google or Microsoft sign-in app (`GOOGLE_CLIENT_ID` / `MICROSOFT_CLIENT_ID` with their secrets) whose allowed return address includes `/api/mailbox/google/callback` or `/api/mailbox/microsoft/callback`. New firms then send from their preparers' mailboxes, and a client cannot be started until their preparer has connected one.

`TH_MAIL_LAYER=fake`: a stand-in held in memory, for a trial run on one machine. Refused in production.

If Neeter says no to one of the four extensions, the fallback is a setting, not new code: `NEETER_SEND=due_date` (its own follow-up on a due date), `NEETER_REPLIES=poll` (we fetch replies), `admin link-mailbox` (an assistant set up at Neeter by hand). `docs/neeter/RUNBOOK.md` has the table, the conformance suite against Neeter's sandbox (`npm run test:layer`), the connection check, the admin commands and how to take the layer out again.

## Before any real client is contacted (spec section 9)

None of this is code, and none of it is done: an hour with counsel on the Safeguards Rule and Section 7216 (whether form and issuer names sent to the layer are tax return information; where Neeter's people and servers are); each pilot firm's insurer; a signed agreement with Neeter (white label, data processing, location, deletion, breach notice in 72 hours, no training on content); a security plan addendum for each pilot firm; Neeter named as a subprocessor in the data processing terms (`docs/SECURITY.md` has the entry, with the hosting location still to be filled in).
